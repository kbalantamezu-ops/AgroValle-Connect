# REQ-01: Registro de Agricultores. Especificación IEEE 29148 vs. BDD

Este documento especifica el mismo requisito (HU-01 del [`BACKLOG.md`](../BACKLOG.md)) de dos formas: con la plantilla de la norma ISO/IEC/IEEE 29148 y con escenarios BDD (Given-When-Then). Al final se comparan ambos enfoques.

---

## 1. Especificación según IEEE 29148

| Atributo | Descripción |
|---|---|
| **Identificador** | REQ-01 |
| **Nombre** | Registro de agricultores |
| **Enunciado** | El sistema deberá permitir que un agricultor se registre mediante `POST /api/v1/auth/register`, enviando su nombre, cédula, correo electrónico, contraseña y municipio del Valle del Cauca, y deberá persistir el registro en la base de datos PostgreSQL. |
| **Justificación** | Sin un agricultor registrado no es posible publicar productos (HU-02). El registro es la puerta de entrada de la oferta agrícola de la plataforma. |
| **Fuente** | Historia de Usuario HU-01 del Product Backlog. |
| **Prioridad** | Alta (*Must Have* según MoSCoW). |
| **Estimación** | 3 Story Points. |
| **Método de verificación** | Prueba (pruebas unitarias con JUnit 5 y prueba del endpoint con Postman o Swagger). |
| **Criterio de aceptación** | Ante datos válidos, el sistema responde `201 Created` y el registro queda almacenado en PostgreSQL. |
| **Estado** | En desarrollo (Sprint 1). |
| **Trazabilidad** | HU-01 → T01.01 a T01.06 (`sprint-1-planning.md`) → tabla `agricultores` del DER → `AuthController`, `AgricultorService`, `AgricultorRepository`. |

### Requisitos derivados

| ID | Enunciado | Verificación |
|---|---|---|
| REQ-01.1 | El sistema deberá rechazar el registro si la cédula o el correo electrónico ya existen. | Prueba |
| REQ-01.2 | El sistema deberá almacenar la contraseña cifrada con BCrypt y nunca en texto plano. | Prueba / Inspección de código |
| REQ-01.3 | El sistema deberá validar que el correo tenga formato válido y que los campos obligatorios no estén vacíos, y responder `400 Bad Request` en caso contrario. | Prueba |
| REQ-01.4 | El sistema deberá asociar el agricultor a un municipio existente del Valle del Cauca. | Prueba |

### Calidad del enunciado (verificación de las características de la norma)

- **Necesario:** sin el registro no existe oferta que publicar.
- **No ambiguo:** define endpoint, datos de entrada y resultado esperado.
- **Verificable:** se comprueba con el código de respuesta `201` y la fila en la base de datos.
- **Singular:** el enunciado principal trata una sola capacidad. Las reglas adicionales se separaron en requisitos derivados.
- **Factible:** es alcanzable con Spring Boot y PostgreSQL en 3 Story Points.

## 2. Especificación en BDD (Given-When-Then)

### Escenario 1: Registro exitoso

- **Given** que el usuario ingresa a `/api/v1/auth/register`.
- **When** envía un JSON con `nombre`, `cedula`, `email`, `password` y `municipioId` válidos.
- **Then** el sistema responde con status `201 Created` y el registro persiste en la base de datos PostgreSQL.

### Escenario 2: Cédula duplicada

- **Given** que ya existe un agricultor registrado con la cédula `123456789`.
- **When** otro usuario intenta registrarse con la misma cédula.
- **Then** el sistema rechaza el registro y responde con un error, sin crear un segundo agricultor.

### Escenario 3: Datos inválidos

- **Given** que el usuario ingresa a `/api/v1/auth/register`.
- **When** envía un correo con formato inválido o deja un campo obligatorio vacío.
- **Then** el sistema responde con status `400 Bad Request` y un mensaje que indica el campo incorrecto.

## 3. Comparación: IEEE 29148 vs. BDD

| Criterio | IEEE 29148 | BDD (Given-When-Then) |
|---|---|---|
| **Propósito** | Documentar formalmente qué debe hacer el sistema. | Describir ejemplos concretos de comportamiento que se puedan probar. |
| **Estructura** | Tabla con atributos: ID, enunciado, prioridad, verificación, trazabilidad. | Escenarios con tres pasos: Given, When, Then. |
| **Lenguaje** | Formal: "El sistema deberá…". | Natural y cercano al negocio. |
| **Audiencia** | Ingenieros, documentación y auditorías. | Todo el equipo, incluido el cliente o el docente. |
| **Verificabilidad** | Indica el método de verificación, pero no incluye los casos de prueba. | Cada escenario se convierte casi directamente en una prueba. |
| **Trazabilidad** | Muy fuerte: enlaza requisito, diseño, código y pruebas. | Débil: depende de que el equipo enlace cada escenario con su historia. |
| **Ventajas** | Precisión, orden y control de cambios. | Claridad, ejemplos reales y menos malentendidos. |
| **Desventajas** | Más extenso y lento de escribir. | No documenta por sí solo prioridades ni trazabilidad. |

### Conclusión

Ambos enfoques son complementarios. En AgroValle Connect, el formato BDD sirve para definir los criterios de aceptación de cada historia y escribir las pruebas de JUnit, mientras que IEEE 29148 sirve para formalizar los requisitos más importantes, justificarlos y trazarlos hasta el código y el diseño de la base de datos.
